# Introduction #
For my AI project, I decided to attempt and levarage _local_ AI , in an attempt to understand what the current landscape is for self hosting model with the goal of devoplement. While I know it might deviate
from the original outline, I believe that this experience has been extremely valuable overall, and made me familiar with agents as a whole. 

To fully test running local AI, I also had the idea of _completley_ reworking the functionality of the provided starter code, to attempt and gauge an agent's reasoning ability (locally of course).
This project taught me many lessons, which I will elaborate on later.

## Prologue ##

I originally planned to use my laptop to complete this assignment, as I would mainly be on campus. My laptop has 16GB DDR5 RAM, as well as a 5.10 GHz processor. However, when even just using the _7b_ parameter 
model, by laptop began overheating immenesley. So much so, where I had to make a bootleg heatsink with an old-pan and icepackets to prevent it from overheating. Responses took multiple hours, and in the end I
decided to move to my desktop, with a dedicated GPU

## Specs: ##
- Nvidia RTX 3060 12GB VRAM
- 3.6Ghz Processor
- 32GB DRR4 RAM , 3200 MGhz

The main bottleneck was my CPU. Moving data and responses from the GPU and back severley strained my CPU. I would notice during inference, my CPU usage would be fine, however, once the response began, I would
experience almost 100% usage. RAM was not an issue, but I noticed degraded performance as time went on in the same conversation. I would need to frequently restart the model, and begin fresh. Over time,
with longer context, my RAM usage would range from 4 GB to 11 GB depending on the length of the conversation.

# Workflow #

Through the use of aider:
- aider --no-auto-commit --model ollama_chat/qwen2.5-coder:14b
I would prompt it to make changes to codebase iterativley. I had to be exteremley accurate and precise. I removed the agents ability to auto commit after a specific commit almost ruined my git repositiory. I would
create commits myself to always ensure I could revert to a workable state.

I had to be extremley specific in what files to edit, and what to do. In a case where I wasn't, it ended up creating an entirely new file, with redundant functionality, which was never used. It would
implement changes on said file, claiming to have adressed my concerns.

Once I knew I had to be precise in my prompts, the local model was quite helpful. However, it was terrible for debugging. For implementing new features (as I didn't know React, Tailwind, etc.) I would 
prompt the model, and for debugging I would do it myself. The fact that the model was running locally made me consider if a specific question was 'worth' it, versus if I was using a cloud model.

For example, I can simply use nvim $s: ----- : ----- to replace elements vs asking the model to do it.

Towards the end, I did end up asking Gemeni specific questions regarding styling. However, I would ask Gemeni a general question , and with the new knowledge, prompt my local model. So all source code was
generated by the local model, or made by me.

I at one point used the 32B paramater model to make a huge amount of changes. While it did work, since the scope was broad, it introduces technical debt I had to adress later when implementing the final styles.

It was helpful for adding debugging statements so I myself could make the changes. However, it was also tricky. At one point, I prompted ' DO NOT MAKE ANY CHANGES ', and it made the changes anyway.

When implementing new features, I had to specifically outline the pseudo algorithm. I could not afford to be vague when querying the model.
